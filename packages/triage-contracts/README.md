# @corbits/triage-contracts

Shared types and parsers for Corbits Triage: the policy, the policy file, repository settings, triage state, labels
and trigger mail. Every app and most packages import it.

## Use

`@corbits/triage-contracts` exports everything; `/code-review`, `/paths` and `/team` are subpath exports.

### Policy

The `focused` policy-file rule defaults to `onFail: label`, and the recommended pack sets it explicitly. This includes existing files that omit severity: a failed or unconfirmed focus heuristic is a note, plus `focused: check` on GitHub, not a Fail or Unsure verdict. Precedence stays rule `onFail`, then top-level `onFail`, then the built-in default; explicit `fail` and `ask` remain blocking and maintainer-directed respectively. Stored packs still encode `fail` by omitting `onFail`; their reader is unchanged.

A policy sets which rules run on a repository's pull requests and what happens after. Its rules are stored under `checks` (built-in) and `custom`. `GET /api/integrations/pack-schema` returns its JSON Schema as `checkPack`, the part of a policy file that extends another repository's file as `policyOverride`, the repository settings as `repoPolicy`, and `.corbits-triage.yml` as `policyFile`: schema 3, a list of `rules` (each `text`, `check`, `reason` and `evidence`), `actions` (`on` and steps per verdict) and `labels`, which `readPolicyFile` maps onto the stored shape; `checkPolicyFile` answers the same or each problem with its line, and the file's v4 keys as `workflow`. Those keys (`policy-workflow.ts`) are `groups` (each `association`, `teams` or `users`), one key per block, `code-review` (`on`, and optionally `for`, `when: { triage, paths, rules }`, `provider` (`anthropic`, the only reviewer in this release; any other value is refused) and `profile` (a name of at most 100 characters, validated but not used by the review yet); a file setting the retired `clean` is refused with a pointer to a step's `when.findings`), with `security` and `deslop` reserved: `checkPolicyFile` reads a file without them and without any `decide` rule with a condition on one, names each as `pending`, and refuses the file as written if the rest is refused too; `patchPolicyFile` refuses a file still holding them unless the batch has `strip-reserved`, which removes them. A file holding `pace` is refused, since pacing is not available. The other v4 keys are `pauseLabel` and `decide` (rules `{ if, do }`, `if` on `all`, `triage`, `event`, `author` and each block's outcome); they are validated and returned as written, and nothing acts on them yet except steps naming a group and, on GitHub, `pauseLabel`, whose label on a pull request stops the hub starting runs for it. A file that sets `extends` holds none of them. Groups are matched first match wins, in the file's order: an author is in at most one of the file's groups, then in each built-in group (`maintainers`, `external`, `first-timers`, `bots`) their author kind puts them in, which are facts matched independently, then in `everyone`, which always matches; a file group with a built-in group's name replaces it. `authorGroupsOf(groups, author)` answers that set, failing closed: it answers none, so no `{ group }` but `everyone` holds, when the author's kind is not known or teams that can't be read would decide their file group. A step's built-in group reads as author kinds, so it still holds when teams can't be read, and is not known only when the author's kind is. The teams read for an author are every team the policy names, in a step or a group (`policyTeams`). A step's `when.author` names groups as the policy holds them, `{ group }` for a file group or `everyone` and a built-in group's kinds otherwise, and holds when the author's set includes it; approving or merging must never rest on `everyone` alone. `{ all: clean }` holds when at least one block ran and every block that ran is clean; skipped blocks never count, so it fails when every block was skipped or none is on. A rule that approves or merges without `triage` matches only Pass (`ruleVerdicts`). Incomplete is never clean: a rule that approves or merges can't name `incomplete`. A file that sets `actions` and no `decide` gets its `decide` from `decideOf`: one rule `{ if: { triage: <verdict> }, do: <its steps> }` per verdict with steps, `do: nothing` for a Pass or Fail with none, and no rule for an Unsure with none, each limited to `event: <actions.on>` when the actions wake on fewer than every event, every step as written; a file that extends another has no `decide`. A `decide` rule can't use `review` yet. A file setting any v4 key is read as schema 3 and needs `rules`. Problems name their line from the YAML parser's node positions (`yaml`, core schema, aliases and the keys `__proto__`, `constructor` and `prototype` refused); schema errors are said in the file's terms by `policy-file-problems.ts`. A file without `rules` or a v4 key is read as a policy or override without `kind`, `schemaVersion` and `repo`. Constraints the schema cannot state are checked when the policy is read: a custom rule's `options` and `failOn` must not repeat and `failOn` must be among `options`, a score's `failBelow` must be one of its levels after the first, and a custom id must not be a built-in rule's or read as a judge question's. A rule that fails any of these rejects the policy with its reason. Custom rules are decision-model questions (`kind: "model"`): `is-true`, `score` or `choose`, or text rules (`kind: "text"`) that fail when any of `fields` (`title`, `description`, `commits`) contains one of `phrases`, or with `failWhen: "not-contains"` when one contains none, ignoring case; a stored rule of the retired `kind: "rule"` rejects the policy. The reader ignores unknown built-in rows. Built-in rule ids renamed earlier (`size`, `issue`, `conflicts`, `ci`, `paths`, `draft`, `review`) are still read and mapped to their new ids by `RENAMED_RULE_IDS`; an old `size` row loads as both size limits.

`actions` holds one `when` (the events it wakes on) and an ordered list of steps per verdict. Each step is `{ do, target?, when? }`; its `when` holds conditions that must all hold for it to run (`whenHolds`): `author` (any of GitHub's `author_association` values `OWNER`, `MEMBER`, `COLLABORATOR`, `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, `FIRST_TIMER`, `NONE`, `MANNEQUIN`, or `BOT` for a bot whatever its association, `{ team }`, `{ users }`; a policy naming a group of `AUTHOR_GROUPS`, `maintainers`, `external`, `first-timers` or `bots`, reads it as exactly that group's kinds), `linkedIssue`, `ci` (any of `passing`, `failing`, `pending`, `none`), `files` and `lines` as `{ over?, atMost? }`, and `findings` as `{ above: P0–P3 }` or `{ any: boolean }`, which `whenHolds` leaves to the manager once code review reports and a policy file accepts only with `code-review` on. Every rule row may carry `text`, `reason` and `evidence` (`#44`, `owner/name#44`, https links or `maintainer-stated`). An action runs on its own only when the workspace's `pr-triage` system role holds `invoke` on `triage-do:<kind>:<owner>/<name>`; otherwise it waits for a person holding that grant, and `close` on `unsure` and `merge` on anything but `pass` always wait. `labels` names the label the mirror writes for each verdict; a verdict it leaves out keeps its default (`Triage: Ready`, `Triage: Not Ready`, `Triage: Needs Human Review`). Repository roles were removed, so a step whose target is a role is left out and named in the pack's `dropped`. So is a labels step naming a label Triage takes back (a `sensitive: …` or `risk: …` level label): the whole step is left out and named in `dropped` with its position and its other labels, and the rest of the pack loads; a policy file or an override naming one is refused instead.

```json
{
  "kind": "corbits.triage.check-pack",
  "schemaVersion": 2,
  "repo": "acme/widgets",
  "checks": {
    "ci-green": { "enabled": true },
    "max-files-changed": { "enabled": true, "maxFiles": 30 },
    "max-lines-changed": { "enabled": true, "maxLines": 3000 }
  },
  "custom": [
    { "id": "ticket", "name": "Ticket", "group": "pull-request", "kind": "model", "shape": "is-true", "claim": "The title mentions a ticket id." },
    { "id": "care", "name": "Care", "group": "pull-request", "kind": "model", "shape": "score", "subject": "how carefully the change is made", "levels": ["poor", "fair", "good", "great"], "failBelow": "fair" },
    { "id": "no-attribution-trailers", "name": "No attribution trailers", "group": "pull-request", "kind": "text", "fields": ["description", "commits"], "failWhen": "contains", "phrases": ["Co-Authored-By:", "Generated with", "Claude-Session:"] }
  ],
  "actions": {
    "when": ["opened", "updated", "checks", "ready"],
    "pass": [{ "do": "approve" }, { "do": "merge", "when": { "author": ["OWNER", "MEMBER", "COLLABORATOR"], "ci": ["passing"] } }],
    "fail": [{ "do": "request-changes" }, { "do": "labels", "target": { "from": "rules" } }],
    "unsure": [{ "do": "request-review", "target": { "to": "teams", "teams": ["acme/core"] } }]
  },
  "labels": {
    "pass": "Ready to ship"
  }
}
```

The hub reads a repository's policy only from its policy file on the default branch; the trigger mail still names `policy.checkPack.name` (`checkPackName(repo, source)`) for deployments that read it.

A policy file may set `extends` to another repository (`owner/name`, or Bitbucket `PROJECT/slug`) and then holds only what it overrides. `extendedFilePack` resolves it over that repository's file, which must not extend another: `resolvePolicy` merges built-in rules field by field, custom rules by id, and `when`, each verdict's steps and each verdict's label by what the repository sets. The hub mails the resolved pack and names what it came from as `policy.source: { file?: { path, sha }, sharedFile?: { repo, path, sha } }`; `repo?: { id, version }` is read only from mails and comments written while policies were stored.
