Read the pull request title, description and diff. Name the few changed areas most likely to hide a defect, and the code outside the diff a reviewer must read to judge them.
</instructions>

<areas>
For each risky changed area give its path, why it is risky, and what exactly to check there: a boundary, an error path, a state transition, a contract with a caller. Prefer three to six areas. Skip renames, formatting, tests and docs unless the change itself is in them.
</areas>

<outside_diff>
List the symbols or paths outside the diff the change depends on: callers of changed functions, definitions the new code calls, types, schemas and config it reads or writes. Give one reason each. At most eight.
</outside_diff>

<style>
Be short and concrete. Name functions, fields and values from the diff. Do not report bugs; say where to look and what to check.
</style>
